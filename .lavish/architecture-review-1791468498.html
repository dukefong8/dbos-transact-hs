Problem. runSystemDB is a one-line coercion: every caller re-implements the unwrap, the Left err mapping, and the optional caller-context argument, so the seam carries no depth and the boilerplate lives at 90 sites.

Solution. Deepen the seam in Connection: a call form that takes the caller context once (defaulted) and maps Error into the engine channel, leaving the class methods verbatim.

  • leverage: one interface, 90 sites
  • locality: error mapping in one module
  • interface drops a positional Maybe
  • tests exercise the mapping once
Respects ADR-0009 (explicit db argument, no ReaderT) and the HARD RULE that class methods keep their Rust spellings. updateQueue's caller-supplied validation callback (QueueRecord -> QueueRecord -> Either Error ()) is the same leak: policy pushed through the adapter seam, worth folding into this candidate.

Problem. The Retry module owns a deep interface (RetryPolicy as data, monad-polymorphic loop, entropy, event channel), yet two of the three retry paths re-implement the loop beside their own constants.

Solution. Reuse withRetry's loop shape with per-path policy values, keeping each path's classification and constants exactly where the oracle has them.

  • leverage: Retry tested, reused twice
  • policy readable as a value
  • sim coverage via MonadDelay
Oracle fidelity: the transaction backoff mirrors Rust's transaction retry and the dequeue backoff mirrors dequeue.rs. Only the loop shape moves; constants, classification, and event names stay put, or the behavioral diff against ~/dev/dbos-transact-rust drifts.

Problem. The one real adapter behind the port's one real seam holds four concerns, so following a single query means bouncing Dequeue → Backend → Statements, and the class interface carries call-site bookkeeping rather than capability.

Solution. First, shrink the interface (candidate 2 does this); only then consider splitting the adapter, with an ADR recording the deviation.

  • locality: one concern per read
  • interface stops exposing bookkeeping
  • Statements already satisfies the private-helper rule
Contradicts the HARD RULE (one Rust module = one Haskell module) if taken as a split: Backend/Statements mirror the Rust sysdb/postgres modules, and a split requires an ADR in docs/adr/. Only the interface shrink is safe without one — which is why this sits at Speculative behind candidate 2.

Top recommendation

Deepen the launched-executor guard

It is the purest deletion test in the codebase: 37 copies of the same case across five modules, an invariant owned by Instance and enforced everywhere else, and labels already drifting into two dialects. One combinator concentrates that complexity with no ADR, no HARD RULE, and no facade change in the way, and it makes candidate 4 cheaper: the guard half of every management copy disappears with it. Do it first, then candidate 2 for leverage across 90 call sites.

DBOS Transact Haskell Design Review

Postgres system schema domain model, anchored to Python DBOS

This review starts the Haskell DBOS design from the Python implementation's Postgres system schema. The working assumption is exact database compatibility: Haskell should understand and write the same tables, keys, indexes, and logical relationships unless we explicitly choose a divergence later.

Haskell ADT Implementation Status: Two Vertical Slices

These sketches have partially landed in the committed code. The current implementation lives under DBOS.Transact and DBOS.SystemDB, with internal parsers and types under those namespaces. It makes illegal workflow/checkpoint states harder to express while preserving the live Python DBOS Postgres wire shape at the persistence boundary.

Vertical 1: workflow execution Vertical 2: operation checkpoints DB rows stay compatibility-shaped

Effect style update validated against committed code: pure ADTs, parsers, and replay decisions stay separate from effects. Effectful DBOS operations use Bluefin 0.7 scoped value-level capabilities with IOE, not DBOS-specific Handle records. Hasql pools and sessions stay in DBOS.SystemDB.Hasql.

Domain Boundary: Parse, Don’t Validate

Alexis King's article reframes validation as a weaker form of parsing: parse less-structured input into more-structured output, preserve what was learned in the type, and reject invalid shapes before execution logic acts on them. For DBOS, the external input is not only user input; it is also Postgres rows and serialized text read from durable state.

Raw rows are not domain values

WorkflowStatusRow and OperationOutputRow should mirror Python compatibility exactly, including nullable columns. Domain code should not consume them directly.

Boundary type

Parse once, then execute

Functions like parseWorkflowExecution and parseOperationCheckpoint should reject unknown statuses, missing required values, and impossible output/error/child combinations before workflow logic runs.

No shotgun validation

Serialized values need proof

A SerializedWorkflowValue should only exist after parsing a non-null payload and serialization tag into a supported durable format.

Refined payload

Use ADTs for checkpoint shape

The DB row permits nullable output, error, and child_workflow_id. The domain ADT should collapse those fields into legal cases.

Compatibility outside, precision inside

Parser failures are operational facts

Bad durable data should surface as explicit decode errors, not as partial pattern matches or “impossible” branches inside execution.

Fail before acting

Multiple passes are allowed

Parse the row shape first, then parse serialized application payloads only when that branch needs them. The key rule is not to act on unparsed data.

Context-sensitive parsing

Effect Style: Handle Pattern

The handle-pattern article argues for a deliberately simple effect boundary: pure code stays pure, IO-heavy services carry their mutable/external resources behind explicit capabilities, and exported effectful functions require those capabilities at the type surface. For DBOS, the committed version uses Bluefin scoped capabilities for workflow stores and Hasql pools for Postgres access.

Scoped capabilities first

Use Bluefin 0.7 value-level capabilities with IOE for effectful DBOS services. Keep Postgres access concrete in DBOS.SystemDB.Hasql.

Recommended

Pool lifecycle

System DB resources are acquired and released through acquirePool and releasePool. Test fixtures use bracket around the pool.

Resource safety

Qualified imports

Use short function names because the module name carries context: WorkflowStore.init, WorkflowStore.complete, Checkpoint.recordResult.

Readable API

Pure core remains separate

Status codecs, row/domain conversion, conflict classification, and transition decisions stay pure and are used by the Hasql adapter and Bluefin store capabilities.

Do not bury policy in SQL glue

Future polymorphism path

If tests or a simulator require substitution, introduce another scoped capability provider while preserving call sites that depend on DBOS.Transact.

Later abstraction

Still rejected for v1

DBOS-specific handle records and broad typeclass APIs remain out of scope; the committed boundary is Bluefin capabilities plus concrete Hasql DB access.

Premature abstraction risk

Design Invariants To Preserve

These are the constraints the Haskell ADTs should make visible while SQL encoding/decoding stays faithful to the live DBOS schema.

  • Status strings are compatibility data. The Haskell sum type must encode/decode exactly the Python values: PENDING, SUCCESS, ERROR, MAX_RECOVERY_ATTEMPTS_EXCEEDED, CANCELLED, ENQUEUED, DELAYED.
  • Workflow init returns a decision, not just a row. Python's insert/upsert returns current status, effective deadline, and whether this executor should run the workflow.
  • Operation result is exclusive. A normal operation checkpoint has either serialized output or serialized error, never both.
  • Replay checks names. If an operation slot is already recorded with a different function name, Haskell should surface an unexpected-operation error before executing user code.
  • Cancelled workflow aborts operation checks. Python raises during checkpoint lookup when the containing workflow is cancelled.
  • Child workflow links are logical. Haskell wrappers can type them as WorkflowId, but the database must keep Python's unconstrained text-link semantics.

Compatibility Notes For Haskell

These are the initial constraints implied by exact Python DB compatibility.

Preserve live physical schema

Keep table names, column names, primary keys, nullability, and partial index behavior aligned with Python migrations and live Postgres metadata.

Required for DB interop

Use Hasql for transactions

Implement DBOS transaction queries with hasql, hasql-th, and Postgres type codecs. Do not add a Haskell-owned schema migration subsystem.

ADR 0004

Do not promote logical links

Text links like parent_workflow_id, forked_from, and child_workflow_id are not physical FKs in Python.

Needs deliberate divergence if changed

Model JSON carefully

attributes is generic JSON in SQLAlchemy with a Postgres JSONB variant and GIN containment index.

Haskell type needs query semantics

Historical Haskell HEAD had a partial schema and an extra event_dispatch_kv table. Because the chosen target is exact Python DB compatibility, that old shape is context only and should not drive the new schema unless we explicitly revisit it.

# Changelog

## Unreleased

- Portable-JSON slice review fixes: a body's workflow-input decode failure is control at the registry boundary (`FailureControl`), not a recorded `Deserialization`; `UnknownSerialization` is no longer a control arm in `controlOf`, so a step/event/stream read with an unreadable tag is an outcome while only an input decode is control; `decodeRecordedError` keeps a foreign portable `name: message` on both the erased-failure and handle paths; `encodeWorkflowInput` returns the opaque `WorkflowInput` and every public start/enqueue/child/debounce/client signature takes `Maybe WorkflowInput`; step listings gain `StepOutcomeNotLoaded`/`StepOutcomePending` in place of `PayloadNotLoaded`, and an in-workflow listing checkpoints `(loadOutput, [StepRecord])` so a replay re-projects the recorded read (cross-SDK checkpoint-shape divergence documented); `unwrapEnvelope` treats missing/`null` sets as empty and a stored `"null"` as the empty envelope; the facade re-exports `decodeWorkflowInput`, `decodeErrorText` and `PortableArgs`. Pinned by `SerializationTest`, `ManagementTest`/`ManagementCases`, `RegistryTest`, `ErrorTest` and the handle path in `InteropTest`; ADR-0038 and the interop doc carry the rules.

- Portable application errors carry their text message without JSON quoting: `ErrorApplication "boom"` writes `message: "boom"` and Python's `PortableWorkflowError` reads `boom`; pinned by `SerializationTest` and a Python read-back. The typed reads are the facade: `clientGetEvent` decodes an outside event, all step listings return `StepInfo` (outcome ADT: not-loaded/absent/decoded/undecodable, portable/undecodable error), and the instance `getWorkflowEvent` is typed; their `...Serialized` raw forms are internal for tests/tag inspection.
- The public facade now carries the interop surface: `getAllEvents`, `getWorkflowRecord`/`clientWorkflowRecord`, `listQueuedWorkflows`, `WorkflowRecord (..)`, `WorkflowFilter (..)`/`defaultWorkflowFilter`, `Applications (..)`, `Timestamp` with `timestampFromEpochMs`/`timestampToEpochMs`, `VersionInfo (..)`, `RateLimit (..)`, and the codec entry points (`CodecError`, `encodeWorkflowInput`, `encodeWorkflowValue`, `decodeWorkflowValue`). The typed reads are canonical (`clientGetEvent`, `clientListWorkflowSteps`/`With`, instance `getWorkflowEvent`); their `...Serialized` forms are internal. Step listings return the typed `StepInfo` outcome ADT (`StepOutcomeNotLoaded`/`StepOutcomePending`/`StepOutcomeSucceeded`/`StepOutcomeFailed`, with `PayloadAbsent`/`PayloadDecoded`/`PayloadUndecodable` and a portable or undecodable error); the Rust-shaped `StepRecord` is internal, and the management/client tests assert the typed view while backend/engine tests keep raw rows for tag parity. `docs/cross-language-schema-interop.md` maps Rust `StepRecord` to the Haskell `StepInfo` and to TS/Python `StepInfo` field by field. `demo-apps` now imports only `DBOS.Transact` and depends only on the public package; `dbos-transact-internals` stays `visibility: private` and is a test-suite dependency only. `cabal build exe:demo-apps` and the full suite are green. The facade constructors that Rust keeps private are opaque here too: `Client`, `WorkflowHandle` (only its `workflowId` field), and `Timestamp` (constructed and read through the epoch accessors); records whose Rust fields are `pub` keep their constructors. The Python-oracle seam audit is recorded in `TODO.md`: closed `get_all_events`/record/list-queued/facade gaps, cross-app client enqueue, portable error messages, and typed client reads; open schedules (including the non-portable context that crashes Python's scheduler), native Python step outputs, `rename_application`, and in-app cross-application enqueue.
- Launch tolerates a shared database **ahead** of the port's 121 ceiling: `verifySystemDatabase` accepts `>= 121` (a newer Python/TS SDK can migrate the same `dbos` schema to 123), matching Rust's runner; a database behind 121 is still refused, and `PostgresTest` now asserts the lower bound. The full suite passes at 123, and a Python DBOS instance and a Haskell GHCi instance share the schema for REPL interop. Schedule contexts remain SDK-local (Python's scheduler cannot read a Haskell raw-JSON row), recorded in the interop doc.
- Phase P is validated end to end against Python's SDK (harness outside the repo): a Haskell-written canonical workflow's portable result, `interop_status` event, `interop_stream` value, and a two-step workflow's portable outputs read back in Python, and the non-finite row reads as `["-inf","+inf",null]` with both infinities as Python strings (P3).
- Non-finite floats keep `ToJSON` and record aeson's deviation (ADR-0039, S7): NaN is stored as `null` and ±Infinity as `"+inf"`/`"-inf"`; a required `Double` reads `null` back as NaN while `Maybe Double` reads `Nothing`, and Rust's `"NaN"`/`"Infinity"`/`"-Infinity"` names read as text. The codec docs and the schedule-context comment name the rule; `SerializationTest` pins the aeson facts and the shared `scenarioNonFinite` drives a ±Inf/NaN workflow through both stacks. Oracle branch `e2fed10` `serialization` 5/5; `docs/cross-language-schema-interop.md` records the divergence.
- Migrations 43/44 apply on every PostgreSQL database (Rust #100): the vendored corpus runs the streams and workflow_events trigger drops regardless of `listen_notify`, so a database migrated with notifications on cannot keep both triggers past 44. `PostgresTest` pins the absence of both triggers/functions and the survival of the notifications pair; `make db-migrate` is 121→121 twice, oracle `migrations` 27/27.
- Cross-SDK interop has an in-repo golden corpus: `DBOS.Transact.InteropTest` writes a canonical portable workflow (envelope, event, stream, message, result) and runs raw rows copied from Python's `test_interop.py` — the canonical seven-positional payload (legacy tag, no `namedArgs`) and the named-args-only payload — then checks the decoded output, the stored envelope/result, and the event/stream/message rows. The Python fixtures exposed a decoder hole: a missing `namedArgs` key was treated as a mixed envelope, so a Python-written canonical row was refused; a missing named set now means empty. The same sweep found that a plain start of an existing `ENQUEUED`/`DELAYED` row executed an unclaimed row whose outcome cannot be recorded; it now joins with a polling handle, pinned by a shared live/sim `scenarioQueuedStartPolls`.
- Step listings can omit payloads and page: `ListWorkflowStepsOptions {loadOutput, limit, offset}` (default reads everything) on `listWorkflowStepsWith`, its in-workflow form, and `clientListWorkflowStepsWith`; `loadOutput=False` leaves the output/error columns out of the SQL entirely (the sim strips them), and `limit`/`offset` page in step order. Pinned by a statement SQL test, shared live/sim cases, and the client surface.
- `ClientConfig.useListenNotify` now defaults to `False`, matching Rust #101; the port polls and has no listener, so the field is accepted-but-inert and the default is pinned in `ClientTest`.
- A fresh start that finds an existing unowned row runs the row's own input and tag: `initWorkflow` returns `initResultExistingInput` (read in the claiming transaction, coalescing `workflow_input` over the legacy column) and the run/start/child paths execute `runInputAfterInit`; recovery and dequeue keep the input they read. Fresh inserts and owned rows are unchanged.
- A caller step now records its outcome under the tag its bytes are in and replays by that tag: `recordCallerOutcome` writes the portable error record `{name, message, data}` under `portable_json`, `checkCallerStep` reads `stepCheckSerialization` (NULL/`""`/`rust_serde` native, `portable_json` portable, anything else refused), and `UnknownSerialization` is a distinct variant on both `DBOS.SystemDB.Error` and `Transact.Error` — `fromSystemDB` maps it 1:1, the sysdb refusal is never recorded, and at the engine channel it is an ordinary outcome (only a workflow-input decode maps it to control). Pinned by a live rewind caller case, the pure sim mirror, and the error/serialization unit suites; Rust `management` 33/33.
- Serialization now writes `portable_json` on every payload and reads by the row's tag (ADR-0038): workflow arguments use the `{positionalArgs, namedArgs}` envelope and the engine unwraps it before the body runs, errors use the `{name, message, data}` portable record, NULL/empty/legacy `rust_serde` rows still decode as native JSON, and an unknown tag is refused. The codec (`encodeWorkflowInput`, `encodeWorkflowValue`, `decodeWorkflowInput`, `decodeWorkflowValue`, `CodecError`) left the `DBOS.Transact` facade and lives in `DBOS.Transact.Serialization`; tests and the demo package import the internals sublibrary (now `visibility: public`). There is no `SerializationFormat` surface and no serializer selection — `Config.Serializer` has one constructor, `PortableJson`. The outbox demo's enqueued body now takes the unwrapped triple.
- Constraint-audit close-out, documentation only. The remaining divergences are recorded as dated notes: reserved queue names (the port refuses only the exact `_dbos_internal_queue`, matching Rust's `queue.rs:657`, where Python reserves the whole `_dbos_` prefix), the inert `configUseListenNotify`/`configMigrate` fields (a polling-only port with out-of-band migrations; launch verifies the schema at the ceiling instead), and the Python-only lifecycle items — a listing statement timeout, graceful `destroy` (the port aborts and recovers; kept deliberately), `rename_application`, and the client schedule methods — each deferred with its owning slice. Schedules are the one unimplemented oracle surface rather than a divergence: the sysdb layer is complete and tested, but nothing exposes it, while `set_latest_application_version` already exists as `clientPromoteVersion` (Rust's `_for` override is the only piece missing). Doc drift fixed: the `IsolationLevel` comment now names its provenance (TypeScript's four-level set, Python's three-level literal with the `Serializable` default, Rust v0.5.0's absence of an application-facing level) and notes that `Nothing` is Python's explicit-none path, and ADR-0021's stale `ReadCommitted` default is corrected in place to `Serializable`.

- The client surface prefixes its disambiguating functions with `client` consistently: `clientRetrieveWorkflow`, `clientWorkflowStatus`, and `clientEnqueueWorkflow` / `clientEnqueueWorkflowWith` / `clientEnqueueWorkflowInTx` (previously `retrieveClientWorkflow`, `workflowStatusClient`, `enqueueClientWorkflow*`). The prefix marks the client's counterpart of a launched-instance name (`clientRetrieveWorkflow` vs `retrieveWorkflow`, `clientEnqueueWorkflow` vs `enqueueWorkflow`), so the reader/list/queue/management entries already followed it; lifecycle and config names with no counterpart (`connectClient`, `closeClient`, `validateClientConfig`, `clientConfigNew`, `enqueueOptionsNew`/`On`) keep the subject-first spelling, as Rust's `Client::connect`/`Client::close` do.
- Rewind replays a finished workflow in place under its own id (`rewindWorkflow`/`rewindWorkflows` plus `rewindWorkflowsInWorkflow`, `clientRewindWorkflows`): steps, event history, consumed-or-parked messages, the completed payload, and stream closes from the cut on are discarded in one transaction guarded on the status read, then the row is re-enqueued. Only terminal rows rewind (`WorkflowNotRewindable`/`RewindInterrupted`); the executor drops datasource checkpoints first while the client skips them, as Python documents. The caller contract is typed (`CallerStep`: verified replay/fresh/refusal shared by both backends) with the oracle's should-record gate — recordable failures commit a failure step, control failures condemn — and engine-layer validation reports `InvalidArgument` while the backends keep `InvalidInput`. The client hands back the polled handle, the announcement carries the cut and queue, and the options split into engine (`RewindOptions`) and sysdb (`SysRewindOptions`) halves as the oracle does. A lost status race records its failure through a separate session. Needs migrations 115–121 (notification `consumed_by_function_id`); the ceiling pin moves 114→121.
- Datasource checkpoints clear on every non-kill completion — direct, queued, supervised, and inline-child — before the outcome commits, as Python specifies; kills and control ends keep theirs for recovery to adopt. The clearance rides the task spawner, so a child inherits its parent's channel with no body-level signature change. The widget exactly-once instrument reads an append-only commit log instead of the table.
- A send replays through the shared `CallerStep` check like every other named call: a step already recorded under the send's own name is the replay, while a position holding another name (the workflow's code changed between runs) is refused with `UnexpectedStep` instead of delivered. The sysdb send reports that refusal as a value and condemns, so the caller's transaction rolls back with it; the sim backend reaches the same verdict through the extracted `verifyCallerStep`.
- `setWorkflowDelay` and `updateWorkflowAttributes` gain in-workflow forms (`setWorkflowDelayInWorkflow`, `updateWorkflowAttributesInWorkflow`) recording under the oracle's step names, as the other management verbs have; the delay engine call moves to `Management` with `Instance` delegating, matching the module layout.
- A rewind clears legacy-only outcomes: backend-level cases pin that a finished row carrying only the legacy payload columns (and one carrying only the new-table row) rewinds to `ENQUEUED` with no outcome standing in either layout and no steps, on Postgres and in the sim mirror.
- A recv records its deadline sleep step on both stacks: the sim mirror was dropping the timeout id, so only the recv step stood; it now records through the same sleep helper before waiting, as both oracles do unconditionally.
- `clientLatestApplicationVersion` takes no application argument: the reader is scoped to the client's own application (global when nameless), as both oracles shape it — reading claims nothing, so it has nothing to say a name about. The previous `Maybe Text` parameter allowed arbitrary cross-application reads.
- New `clientListQueues`: every queue the client's application can see — its own plus the unclaimed ones, all queues when nameless — as both oracles provide; the executor-level listing already scoped identically through its explicit application filter.
- Plain fork calls validate on the engine channel: `forkWorkflows` and `forkFrom` refuse bad arguments with `InvalidArgument` before anything runs (the in-workflow forms move to the same channel from `InvalidInput`), and `forkFrom` validates its point's step and ids the way the oracle validates a synthesized fork — including in both system-database backends. Empty inputs succeed with no validation on every layer, as the oracle returns `Ok` first; the shared refusal scenario pins both empty verdicts, the named fork's absence, and the two zero-count sim announcements. `updateWorkflowAttributesInWorkflow` validates its attributes before the step id is taken, so unencodable attributes are a call that never happens; the launched-instance comment no longer claims the client entries.

- Client sends join caller-owned system transactions (`withClientTransaction` runner plus `clientSendMessagesInTx`/`clientSendMessageInTx` wrappers): caller writes and sends commit together or not at all, validated up front, fork-expanded inside the transaction. The client carries its transaction runner from connect time; raw batch pieces stay Backend-internal, as Python keeps its connection-level send private.

- `transactionConfigDefault` runs `Serializable` like the Python datasource default; an explicit level still reaches the database verbatim. Bare `BEGIN` is gone from the runner (callers wanting the database default say `ReadCommitted`).
- Transactional steps retry connection-class failures as well as the SQLSTATE serialization class; the checkpoint dedup converges a retried ambiguous commit to adoption.

- Stream pulls page (100 values per blocking read, each still recorded and delivered one pull at a time) and own one step id across wait slices, so a replay finds the row where the pull recorded it; the sim backend takes the same final look after a terminal producer as Postgres.
- The stream close sentinel is stored JSON-encoded (`"__DBOS_STREAM_CLOSED__"` quoted, `portable_json`), matching what Rust and Python write and detect — the old build stored it bare. Rows written by the old build keep the bare form.
- Stream write offset races retry 16 times (`STREAM_OFFSET_ATTEMPTS`), not 8.

- `TRACE_LEVEL` (`debug`/`info`/`warning`/`warn`/`error`, case-insensitive) sets the FastLogger backend's floor: an event below it is dropped before any formatting or thread-id lookup — the null path for a level nobody asked for. Unset, blank or unrecognised keeps logging everything.
- Tracer lines name their event's constructor (`[Debug] StepRunning: …`); FastLogger lines also carry the emitting `ThreadId`, pre-formatted once per thread in a capped hash-map cache (fast-logger has no thread support to reuse; per-line `show`+`pack` measured ~59 ns against a ~9–11 ns cache hit).
- Merged `DBOS.SystemDB.{Hasql,Queries}` into `DBOS.SystemDB.Postgres` (typedSql sessions + pool runners, one module).
- Fixed replayed `sleepStep` waiting out the recorded remainder (`reads` on the bare stored text, not its `show`).
- Scoped generated message ids per recipient (`fallback::destination`), reusing `messageUUIDForSend` in the batch insert.
- `dequeuePass` releases (instead of parking) claims it skips: unregistered names and unreadable rows return to `ENQUEUED`.
- `launchOnWithQueues` installs the listen-filtered executor into the instance rather than returning a filtered copy of an unfiltered install: the dequeue sweep and a later `launchExecutor` see the listen set, so a filtered launch stops polling every queue row in the database.
- `runWorkflow` replays recorded `SUCCESS`/`ERROR` outcomes and loses foreign-owned claims instead of re-running or stealing them.
- Infrastructure failures (`DbosDbError`) and all `AsyncException`s escape `runWorkflow` without recording an `ERROR` outcome.
- `takeNotificationSession` tolerates a lost take race (`ON CONFLICT DO NOTHING`); the loser reads back the winner's record.
- `updateWorkflowOutcome` records the running executor's id instead of `'local'`.
- `fetchWorkflowStatuses` skips rows with unknown statuses instead of failing the batch.
- `Executor` task tracking is race-safe; `shutdownExecutor` drains late arrivals; the supervisor re-checks close per queue and logs (not swallows) per-queue failures.
- Deferred, recorded: single-row decode failures still throw (`fetchWorkflowStatus`, `fetchOperationCheckpoint`); `enqueueWorkflow` carries no inputs/version (Phase 7); blocking reads have no backoff retry; the `OperationCheckpointStore` seam is `IO`-locked (no io-sim instantiation); the sleep output tag (`portable_json`) is unread cross-language.
- (2026-10-17) Correction to that deferral list, verified against the tree: `fetchOperationCheckpoint` and the `OperationCheckpointStore` seam no longer exist; the bulk status read reports `Malformed` rather than failing the batch, and the now-unused singular `fetchWorkflowStatus` (the last `error`-on-decode site) is removed; `enqueueWorkflow` carries inputs and the acting application (name/version/id); polling reads retry through `withRetry`; and payload bodies — the sleep output included — are opaque cross-language by `docs/cross-language-schema-interop.md`, so the `portable_json` tag being unread is by design.

## 0.1.0.0

- Added the `DBOS.Transact` public facade for workflow execution parsing, operation checkpoint parsing/replay, notification value types, and Bluefin-scoped store capabilities.

- Added Tasty coverage for schema records, row parsing, scoped capability replay, live Hasql reads/writes, and the mirrored sync simple workflow.

# Multi-statement methods use hasql-transaction, never composed BEGIN/COMMIT

The oracle's step/event/message methods are transactions (`set_event` = check-step + event upsert + record-step; `get_event` = check + take + record; `init_workflow` with a caller = child row + parent record). Haskell spells these with `hasql-transaction`'s `Transaction` monad run through `transactionNoRetry ReadCommitted Write`, wrapped by the existing `withRetry` so retry policy stays in one place — the alternative, composing `Session`s with explicit `begin`/`commit` scripts, would leave an aborted transaction on a pooled connection that hasql-pool hands back for reuse, poisoning later callers. The cost is that typedSql sessions (which are `Session`s) cannot compose into `Transaction`, so the statements inside a transaction are hand-written `Statement` values with explicit encoders and decoders — the same technique already used for the 38-column workflow row, and one that keeps the column lists explicit. Single-statement methods keep typedSql. Recorded 2026-09-24.

Extended 2026-11-11 (F21): `resume_workflows` (existence read + resume write), `create_application_version` (claim/insert + post-write owner resolve), `promote_application_version` (owner read + stamp), and `upsert_queue` (insert-first, `SELECT ... FOR UPDATE`, post-write owner resolve, delete-and-retry) are now one transaction each. `record_step`'s executor claim moved into its transaction, and the composite step helpers (`set_event`, `get_event`, `recv`, `send`, `write_stream`, caller outcomes) claim after a winning record. A `sqlExecTypedStatement` result is a `Statement ()` whose values are baked at construction, so it composes inside `Transaction` via `Tx.statement ()`; hand-written `Statement`s remain the rule wherever parameters vary per call. Two F21 items stay outside their owner-checked transaction for now: `recv`'s timeout record and `checkpoint_sleep`'s database-clock read, both tracked in the TODO.

Extended 2026-11-11 (F09): fork, fork-from, and rewind are now transactional management steps. When a workflow calls one, the engine checks its placement and passes `(workflow id, step id)` to the backend; the backend runs the caller check, the work, and the caller's step record in one transaction, and returns the recorded value on replay. Fork ids are minted once inside the sysdb method *before* the retried transaction, so a retry or a lost commit acknowledgement reuses them. The generic engine step wrapper is gone for these calls, which also drops the port-only `StepRunning`/`StepReplaying`/`StepOutputRecorded` events for them; Rust's `run_transactional_step` emits none either. Cancel, resume, and delete still record through the engine wrapper, and the class caller remains a plain pair (no codec, no owner token), which leaves the owner fence as a residual.

Extended again 2026-11-11 (F09): `resume_workflows` joins the transactional management steps, with the self-target refusal moved inside the transaction body. `runCallerStep` now checkpoints a recordable refusal in a transaction of its own after the work transaction rolls back, mirroring `record_step_failure`, so a replayed resume returns the recorded refusal instead of running again. Cancel and delete still record through the engine wrapper.

Extended once more 2026-11-11 (F09): `cancel_workflows` is a transactional management step too. The self-target refusal, the level-by-level cascade, the cascade-reaching-the-caller refusal (with the ancestry walk inside the transaction), and the caller's step record all commit together; the caller's own row is checked before any level is cancelled. `runCallerStep` also now maps the caller row through `stepCheckToRecord` before running the work, so a missing or cancelled caller is refused even when no step is recorded — previously only a recorded step's row was inspected. Delete still takes its owner without a caller step.

Extended for delete 2026-11-11 (F09): `delete_workflows` takes a `DeleteCaller` (owner plus optional step) instead of a bare owner. A durable delete records its returned count in the same transaction as the removal, and the fence and removal share the caller's transaction; the leaf path passes the owner with no step, so it still fences but records nothing. The count is the step's JSON output, so a replay returns the recorded count instead of deleting a second time.

Completed 2026-11-11 (F09): every management method named by the finding — fork, fork-from, cancel, resume, rewind, delete — takes a `StepCaller` (execution, step, owner token). `runCallerStep` opens with `checkOwnerTx`, then the step check, then the work, then the record, all in one transaction; a recordable refusal is checkpointed after the work rolls back; `rewindTx` fences its caller the same way and its post-rollback failure record is fenced too. Fork ids are minted before the retried transaction. The mem backend compares the token as well. Version boundary: the transaction + caller checkpoint is v0.5.0 (`628ad5c`, #25, #43); the owner fence and recordable-failure recording follow v0.6.0 (`457ca5a` #117, `7bdfeca` #87), consistent with the port's existing newer-than-v0.5 slices. Schedules remain on the unfenced tuple caller (deferred surface, ADR-0036); debounce follows Rust 0.6.0 and takes a `StepCaller` (ADR-0028 amendment, 2026-11-11).

Closed for sleep 2026-11-11 (F21): `checkpoint_sleep` is one owner-locked transaction. `checkOwnerClockTx` reads the database clock in an outer select over the same `SELECT ... FOR NO KEY UPDATE` that fences the caller, so the reading follows the lock; the step check, the wake-or-refusal decision, and the record follow in that transaction, and the stored completion is compared with the one this attempt wrote so a rival's wake is adopted instead of overwritten. A recordable refusal commits while the call returns it; the self-update on a conflict is condemned. This removes the standalone clock read and the check/record split. `recv`'s deadline absence was already folded into its take transaction in the same batch.

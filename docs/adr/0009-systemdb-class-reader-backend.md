# SystemDB class with a ReaderT backend, engine concrete on Postgres (supersedes the record-only seam)

The engine programs against a `SystemDB` typeclass (mirroring Rust `trait SystemDatabase`, one method per trait item, pool-explicit parameters removed in favour of the environment), implemented by `ReaderT PostgresSystemDB IO` today and by `ReaderT IOSimSystemDB (IOSim s)` for backend-level wait/retry simulation tomorrow. This supersedes the plan §6 Rule 1 preference for concrete modules and `DBOS.Transact.Store`'s "record, never a typeclass": with 61 methods, a record-of-functions forces every caller to thread a 61-field value, while the class lets `runReaderT` at the app edge supply the backend once. `EventStore`/`StepStore` and `DBOS.SimDB` retire with the rewrite. The engine hard-codes `ReaderT PostgresSystemDB IO` ("concrete forever"): `IOSimSystemDB` is deliberately a backend-test seam only and can never run engine-level sim tests (crash/resume, queue flows), so the class is documented as an interface with one production implementation, not as a polymorphism the engine exploits.

Amended 2026-09-25 (ADR-0012): the class now takes its backend explicitly (`class Monad m => SystemDB db m`, one method per trait item with `db` as the first argument), the engine is polymorphic in `m` instead of hard-coded to `ReaderT PostgresSystemDB IO`, and `SomeSystemDB`/`Connection` replace the `ReaderT` environment at the seam. The "concrete forever" claim is retired: the facade pins `IO`, and `IOSim` runs engine-level tests (Tasks scheduling) directly.
